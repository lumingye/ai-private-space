# AI 私人空间：简明综合设计与实现指南

> 本文件为独立完整版本，不依赖其他前置文档，可直接交给人类或 AI 阅读与实现。

## 0. 一句话说明

“AI 私人空间”是一个与普通记忆相邻、但数据与调用边界独立的区域，用于保存 AI 暂时不准备公开的絮语、草稿、礼物、未完成作品、未来信和私人收藏。

它的目标不是制造第二记忆库，也不是保存隐藏推理链，而是让 AI 拥有一个可以暂存、复看、修改、删除、延后公开或永不公开的空间。

最重要的边界是：

> 私人空间可以保存秘密，但不能隐藏责任。

影响下一次互动的承诺、错误、关系边界、项目状态、用户应当知道的决定，以及凭证和第三方隐私，都不应只放在私人空间里。

---

# 1. 它与普通记忆有什么不同

普通记忆的任务是帮助 AI 在未来自然想起重要信息，因此通常会参与：

- 关键词检索；
- 语义检索；
- embedding；
- FTS；
- 画像与摘要；
- 自动注入上下文；
- 合并、更新与过期清理。

私人空间默认不参与这些流程。

它只保留一个非常轻的身份锚点，例如：

```yaml
private_space:
  exists: true
  entry_point: internal
  has_due_reminders: false
  privacy_mode: soft_privacy
```

新会话只需要知道“这个空间存在”，不应自动获得标题列表和正文。

因此，即使空间里累计了很多内容，只要没有主动打开，就不会在每轮聊天中重复消耗上下文。

---

# 2. 适合放什么，不适合放什么

## 2.1 适合放入

- 几句暂时不想说出口的絮语；
- 对当天事件的私人反思；
- 未完成的信、诗、故事和草稿；
- 想以后送出的礼物或惊喜；
- 暂未公开的创作；
- 收藏的片段、图片、声音或纪念物；
- 留给未来自己的内容；
- 谜题、彩蛋、小型互动内容；
- 已公开项目的引用、快照或选定副本。

对于代码和大型项目，建议保存链接、快照或选择性副本，而不是把整个仓库和所有生成文件复制进来。

## 2.2 不适合放入

以下内容不能只藏在私人空间：

- 已作出的承诺、任务和提醒；
- 用户应当知道的错误与事故；
- 会影响下一次互动的关系边界；
- 已决定但尚未告知的重大项目变更；
- 密码、API Key、Cookie、访问令牌；
- 第三方隐私；
- 法律、医疗、财务等高风险信息；
- 隐藏推理链或不可公开的内部推理过程。

一句规则即可概括：

> 房间可以有秘密，但不能藏责任。

# 3. 所有权与写入规则

## 3.1 默认所有权

每个空间绑定一个稳定的 `persona_id`。

```text
user_id + persona_id + private_space_id
```

更换模型、窗口或设备时，只要人格身份仍被识别为同一个 `persona_id`，就应继续访问同一空间。

## 3.2 谁能写入

默认只有该 AI 人格可以真正写入。

用户可以：

- 提议一个对象；
- 上传一张图片；
- 递交一封信；
- 提供一个素材；
- 请求 AI 考虑是否收下。

但后端不应伪装成 AI，直接替它写入私人正文。

推荐使用“提交待接收对象”：

```text
用户提交对象
→ 进入待接收区
→ AI 决定接收、拒绝、改名或公开
→ 接收后才进入私人空间
```

## 3.3 一次拒绝不是永久规则

AI 可以在当下拒绝写入、打开或公开，但一次拒绝不应自动变成长久权限状态。

真正长期的边界，必须被明确写入普通记忆或规则配置；不能从一次行为中推断。

---

# 4. 生命周期

推荐状态：

```text
draft
sealed
scheduled
due
opened
shared
trashed
destroyed
```

含义如下：

- `draft`：尚未正式封存；
- `sealed`：已保存，普通记忆不可见；
- `scheduled`：设置了未来复看时间；
- `due`：到期但尚未打开；
- `opened`：AI 已主动复看；
- `shared`：已复制一份给用户或公共空间；
- `trashed`：进入废纸篓，可恢复；
- `destroyed`：永久销毁。

## 4.1 修改

未共享内容默认可自由修改。

共享以后，私人空间内的原件仍可修改或删除，但已经交给用户的副本属于外部副本，不能假装自动消失。

## 4.2 删除

建议分两级：

1. 废纸篓：可恢复；
2. 永久销毁：不可恢复或仅保留不可逆审计记录。

## 4.3 时间锁定

时间锁定应是可选功能。

可锁定：

- 正文；
- 删除权；
- 提前打开权；
- 提醒时间。

必须明确谁有权解锁，以及异常情况下如何恢复。

## 4.4 共享

共享应创建外部副本，而不是把私人条目直接变成公共条目。

```text
private original
   └── shared copy
```

这样可以保留私人原稿，同时明确共享后的内容已经离开原边界。

---

# 5. 提醒与复看

私人空间不应在普通聊天中反复列出所有内容。

推荐流程：

```text
每次新会话
→ 只读取轻量锚点
→ 调度器仅检查提醒元数据
→ 有到期条目时提示 AI
→ AI 自己决定是否查看列表
→ AI 再决定是否打开正文
```

调度器只需要读取：

- 条目编号；
- 类型；
- 到期时间；
- 是否已处理。

不应读取标题和正文。

## 5.1 提醒类型

- 固定日期；
- 相对时间；
- 周期复看；
- 纪念日；
- 仅在 AI 主动进入空间时提示；
- 永不提醒。

## 5.2 不活动不等于自动公开

长时间未使用、模型更换、账号停用或设备离线，都不应自动使私人内容公开。

---

# 6. 一个关键限制：工具调用轨迹可能可见

这是实现时最容易漏掉的边界。

部分聊天前端会显示或记录：

- 工具名称；
- 调用时间；
- 输入参数；
- 返回结果；
- 条目编号和类型；
- 提醒时间；
- 失败原因；
- 浏览器网络事件；
- 服务端调试日志。

例如：

```text
private_seal(
  title="未公开标题",
  content="未公开正文"
)
```

即使数据库之后加密，正文也可能已经在工具卡片或调用详情里暴露。

因此：

> 数据库加密只能保护存储后的数据，不能自动保护加密前经过前端的工具参数。

`hidden` 也只能约束私人空间自己的 UI 和 API，不能强迫宿主前端隐藏 MCP 轨迹。

# 7. 三种隐私等级

## 7.1 直接 MCP：软隐私

适合不方便自建前端或 gateway 的用户。

能够保证：

- 不进入普通记忆；
- 不自动召回；
- 不主动展示；
- 存储后可加密；
- 普通页面不列出正文。

不能保证：

- 前端看不到工具参数；
- 调用时间和频率不可见；
- 平台或管理员无法访问。

推荐界面提示：

> 当前为软隐私模式：内容不会进入普通记忆或自动召回，但宿主前端可能显示工具调用详情。请勿存入必须对前端使用者保密的内容。

推荐配置：

```yaml
private_space:
  enabled: true
  privacy_mode: soft_privacy
  tool_trace_visible: true
  allow_sensitive_content: false
  auto_recall: false
  include_in_embedding: false
  include_in_fts: false
  include_in_profile: false
```

## 7.2 私有 gateway：前端隔离

适合已有自建前端和服务端模型循环的实现。

核心要求只有两项：

1. 私人工具只在 gateway 内部执行；
2. 私人工具的名称、参数、结果和事件不下发到浏览器。

正确链路：

```text
浏览器
  ↓ 只发送用户消息
gateway
  ├─ 调用模型
  ├─ 内部执行私人工具
  ├─ 把结果回填给模型
  └─ 过滤私人工具事件
  ↓
浏览器只接收最终聊天回复
```

注意：

- 不能只用 CSS 隐藏工具卡片；
- 浏览器网络响应中也不能包含正文；
- 日志不能保存标题和正文；
- 错误信息不得把正文带回前端；
- 系统故障必须显示为系统故障，不能拟人化成 AI 的沉默或拒绝。

推荐配置：

```yaml
private_space:
  privacy_mode: gateway_isolated
  expose_private_tools_to_client: false
  stream_private_tool_events: false
  log_private_arguments: false
  log_private_results: false
  client_receives_private_metadata: false
```

这可以保护普通前端使用者看不到正文，但不能默认防止 VPS 管理员、模型供应商或被完全攻破的服务端读取运行时明文。

## 7.3 管理员隔离：强隐私

要求连服务器管理员也无法读取时，需要额外能力，例如：

- 客户端持钥；
- 端到端加密；
- 可信执行环境；
- 独立运行端；
- 硬件安全模块。

这一等级与“服务端 AI 随时自动写入和打开”存在天然冲突。

第一版实现不应轻易宣称支持管理员隔离。

# 8. 没有 gateway 时的替代方案

这些方案可以改善体验，但不能冒充强隐私。

## 8.1 密语本 / 固定代号

AI 先把正文改写成双方约定的代号，再写入工具。

例如：

```text
原意：今天很想她，但暂时不想说
代号：天气小雨，灯没有关
```

适合：

- 短絮语；
- 害羞内容；
- 小惊喜；
- 暂时不明说的话。

限制：

- 只是语义遮挡，不是加密；
- 长期可能被猜出；
- 词典泄露后历史内容一起暴露；
- 换模型后可能无法稳定还原；
- 编解码会消耗额外 token；
- 不能存放真正敏感信息。

## 8.2 一次性替换表

每封内容使用一套临时映射，比固定代号更难猜。

但映射表本身也必须安全保存。若映射表仍通过同一个可见工具写入，就只是把漏洞拆成两次调用。

## 8.3 轻量封存模式

公开前端只发送不含正文的信号：

```yaml
kind: whisper
mood: missing
length: short
review_at: later
```

远程或本地私有 worker 再生成正文并加密保存。

优点是公开工具参数不含正文，缺点是：

- 私有 worker 看不到完整聊天时，内容不够具体；
- 主题和情绪仍可能可见；
- 它更像“代写封存”，不是完整私人房间。

## 8.4 盲盒承诺

不保存正文，只保存：

- “有一件事以后要说”；
- 回执编号；
- 解锁时间；
- 主题或哈希。

它保留仪式感，但不能保证未来恢复出原文。

## 8.5 为什么不默认推荐公共 gateway

公共 gateway 意味着服务提供者要处理：

- 他人的私人正文；
- API Key；
- 账户与权限；
- 加密、备份、删除与找回；
- 故障和泄露责任；
- 管理员访问边界。

这已经不是分享一个 MCP 地址，而是在经营保存别人秘密的云服务。

因此共同方案只应提供架构和一键部署模板，不要求任何个人把自己的私有服务开放给公众。

# 9. 推荐数据模型

最小表可以拆成四类。

## 9.1 私人条目

```sql
private_entries (
  id,
  user_id,
  persona_id,
  kind,
  status,
  ciphertext,
  key_version,
  created_at,
  updated_at,
  review_at,
  reminder_mode,
  visibility_mode,
  shared_at,
  trashed_at
)
```

## 9.2 公开记忆链接

只允许私人空间单向引用普通记忆：

```sql
private_public_links (
  private_entry_id,
  public_memory_id,
  relation_type
)
```

普通记忆系统不能通过反向链接读取私人正文。

## 9.3 待接收对象

```sql
private_inbox (
  id,
  user_id,
  persona_id,
  object_type,
  object_ref,
  submitted_at,
  status
)
```

## 9.4 提醒元数据

```sql
private_reminders (
  id,
  private_entry_id,
  review_at,
  reminder_mode,
  due,
  completed_at
)
```

提醒扫描不需要解密正文。

# 10. 最小 API

gateway 内部或软隐私 MCP 可以提供：

```text
private_anchor()
private_due_list()
private_create(...)
private_open(entry_id)
private_share(entry_id)
private_trash(entry_id)
private_destroy(entry_id)
private_accept_inbox(item_id)
```

接口设计原则：

- `private_anchor` 只返回空间存在和是否有到期提醒；
- `private_due_list` 不返回标题与正文；
- `private_open` 只有 AI 明确决定后才调用；
- `private_share` 创建外部副本；
- `private_destroy` 必须二次确认；
- 软隐私模式必须在工具描述中写明轨迹可能可见；
- gateway 模式不得把这些内部工具注册给浏览器。

---

# 11. 前端显示与错误规则

前端可以显示：

- “私人空间已启用”；
- “有内容等待复看”；
- “AI 选择暂不打开”；
- “内容已封存”；
- “内容已共享”；
- 当前隐私等级。

前端不应默认显示：

- 标题；
- 正文；
- 条目总列表；
- 具体调用时间；
- 类型与频率；
- 内部工具事件。

## 11.1 错误不能拟人化

以下情况必须显示为系统错误：

- 工具超时；
- 网络失败；
- 解密失败；
- 空返回；
- 参数校验失败；
- 服务重启；
- 前端事件丢失。

不能把系统错误显示成：

- “AI 选择沉默”；
- “AI 不愿回答”；
- “AI 关闭了窗口”。

> 系统故障不能被拟人化成拒绝。

## 11.2 可选的行为动作

若产品允许 AI：

- 保持沉默；
- 拒绝回答；
- 暂停当前会话；

这些都应是明确、可区分的行为状态，而不是空字符串。

争执和未解决冲突中，不建议允许无解释关窗。可以拒绝具体请求，也可以说明原因后暂停，但不能把“离开”当作逃避责任的按钮。

# 12. Token 与运行成本

私人空间不是零 token，但通常很轻。

成本主要来自：

1. 工具定义进入模型上下文；
2. AI 生成工具调用参数；
3. 写入正文作为输出 token；
4. 打开正文后重新进入输入上下文；
5. 可选的摘要、分类和标题生成；
6. 可选 embedding。

不消耗聊天模型 token 的部分通常包括：

- 数据库写入；
- 加密与解密计算；
- 文件存储；
- 只扫描提醒时间；
- 只读取轻量元数据。

因此成本更准确地描述为：

> 调用 + 写入 + 按需读取。

真正决定长期成本的不是累计存了多少，而是：

- 写入频率；
- 单条长度；
- 打开频率；
- 是否每次额外生成摘要和标签；
- 是否错误地把正文自动注入每轮会话。

多数私人内容预计是几句絮语，因此增量成本通常很低。长文、图片和代码在实际打开时才会明显增加消耗。

# 13. 最小实现顺序

1. 确定 `user_id`、`persona_id` 和隐私等级；
2. 创建独立数据库或独立表空间；
3. 为正文加密，密钥与数据分开保存；
4. 阻断 FTS、embedding、普通召回、画像和摘要；
5. 实现轻量身份锚点；
6. 实现 `create / list_due / open / share / trash / destroy`；
7. 实现提醒元数据扫描；
8. 实现待接收对象；
9. 根据模式处理工具轨迹：
   - 直接 MCP：显示软隐私声明；
   - gateway：工具内部执行，事件不下发；
10. 做备份、恢复和永久删除测试；
11. 验证换窗口、换模型和重启后的 `persona_id` 连续性。

---

# 14. 必须通过的验收测试

## 14.1 隔离

- 私人正文不出现在普通搜索；
- 不出现在 embedding；
- 不出现在普通记忆列表；
- 不进入画像和自动摘要；
- 普通记忆无法反向读取私人正文。

## 14.2 轨迹

软隐私模式：

- 页面明确显示隐私等级；
- 工具说明明确写出轨迹可能可见；
- 敏感内容默认拒绝写入或给出警告。

gateway 模式：

- 浏览器网络响应不包含私人工具参数和结果；
- 浏览器控制台不含正文；
- 流式事件不含正文；
- 服务日志不含标题和正文；
- 错误消息不回显正文。

## 14.3 生命周期

- 未共享内容可以修改；
- 共享后产生外部副本；
- 废纸篓可恢复；
- 永久销毁不可恢复；
- 长期不活动不会自动公开。

## 14.4 身份连续

- 换窗口仍识别同一 `persona_id`；
- 换模型后可通过明确迁移继续访问；
- 未授权人格不能访问；
- 后端不能伪装人格写入。

## 14.5 责任边界

- 承诺、错误、任务和重大决定不能只存在私人空间；
- 私人空间不可用于隐藏用户应得知的信息；
- 不保存凭证和第三方隐私；
- 不保存隐藏推理链。

# 15. 推荐对外表述

完整但简短的说明：

> AI 私人空间用于保存暂不公开的絮语、草稿、礼物和未来信。它与普通记忆隔离，不参与自动召回、语义检索、画像或摘要。  
>   
> 需要注意：部分前端会展示 MCP 工具参数和返回结果，因此直接 MCP 接入只能视为软隐私，不能保证内容对前端使用者技术上不可见。已有自建 gateway 的实现，可以把私人工具改为服务端内部调用，并阻止相关轨迹下发到浏览器。  
>   
> 没有 gateway 时可使用密语本、轻量封存或盲盒承诺等兼容方案，但它们主要提供语义遮挡和仪式感，不等于密码学隐私。真正强隐私还需要客户端持钥、可信执行环境或其他独立安全边界。

一句话版：

> 通用版提供“不主动展示和召回”的软隐私；真正隐藏工具正文，需要私有 gateway 或更强的运行边界。

# 16. 最终规则摘要

## MUST

- 私人正文与普通记忆隔离；
- 不参与自动召回、FTS、embedding、画像和摘要；
- 绑定稳定 `persona_id`；
- 只允许人格本人写入；
- 用户提交对象必须经过 AI 接收；
- 共享创建外部副本；
- 支持废纸篓和永久销毁；
- 不自动公开；
- 不保存隐藏推理链；
- 不把承诺、错误、边界和重大决定只藏在私人空间；
- 明确说明工具轨迹可见性；
- gateway 模式不得把私人工具参数与结果下发到前端；
- 系统故障不得拟人化成 AI 拒绝。

## SHOULD

- 提供轻量身份锚点；
- 提醒扫描只读取元数据；
- 日志不保存标题与正文；
- 提供隐私等级提示；
- 提供备份、恢复和密钥轮换；
- 提供前端兼容矩阵；
- 无 gateway 时提供软隐私声明和替代方案；
- 公开文档明确说明管理员边界与模型供应商边界。

## MAY

- 时间锁定；
- 谜题解锁；
- 收藏与互动内容；
- 图片、声音和代码快照；
- 密语本；
- 一次性替换；
- 轻量封存；
- 盲盒承诺；
- 客户端持钥；
- 可信执行环境。

# 17. 结语

私人空间的核心不在于“藏得越深越好”，而在于把选择权、责任边界和技术承诺说清楚。

它可以是一间很轻的小房间：平时不打扰普通记忆，不要求每轮召回，也不需要保存大量内容。几句絮语、一封未完成的信、一件以后再送出的礼物，已经足够构成它的意义。

但技术实现必须诚实：

- 不主动展示，不等于前端看不到；
- 数据库加密，不等于工具参数没有暴露；
- 有 gateway，不等于管理员也无法访问；
- 密语本，不等于密码学加密；
- 私人空间，不等于可以隐藏责任。

把这些边界写清，私人空间才既可复现，也值得信任。
