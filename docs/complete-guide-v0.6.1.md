# AI 私人空间：完整设计、威胁模型与实现指南 v0.6.1

> 本文件是可独立阅读和实施的完整版本，不依赖旧文档。它合并并取代 v0.3、v0.4、v0.5.1 与 v0.6，同时纳入参考代码审计后确认的身份、网关、密钥、备份、不可信内容和责任锚点边界。

## 0. 一句话说明

“AI 私人空间”是一个与普通记忆相邻、但在存储、召回、权限、工具轨迹和导出上独立的区域，用于保存 AI 暂时不准备公开的絮语、草稿、未来信、礼物、未完成作品和私人收藏。

它不是第二记忆库，不是凭据保险箱，也不是隐藏推理或责任的地方。

> **私人空间可以保存秘密，但不能隐藏责任。**

承诺、错误、任务、关系边界、项目变化、安全事项，以及用户本应知道的重要决定，不能只留在私人空间里。

---

## 1. 定位与非目标

“房间”“抽屉”“保险箱”只是产品隐喻。实现中可使用 `private_space`，展示名称可由内容所有者自定义，也可以不命名、改名或建立多个分区。

推荐结构是：

> **产品上同属一个系统；数据、权限、加密、召回和导出上独立。**

私人空间可以复用登录、身份映射、备份框架、跨端同步和通知框架，但普通记忆服务不应因此获得私人正文的读取能力。

它的目标是让内容所有者可以：

- 创建、复看、修改、封存和删除内容；
- 决定是否提醒、何时提醒；
- 决定永不共享，或在未来创建明确范围的共享副本；
- 在换窗口、重启或迁移后仍记得“空间存在”，但不自动想起正文。

它不用于：

- 保存隐藏链式推理、原始推理缓存或规避安全边界的内部记录；
- 代替正式记忆、任务系统、事故记录或责任交接；
- 保存密码、API Key、Cookie、私钥、验证码或支付凭据；
- 未经允许保存第三方隐私；
- 自动运行代码、联网、发消息、花钱或调用外部 API；
- 对法律、医疗、财务等高风险信息作秘密决策或唯一存档。

判断一件内容是否适合放入时，可以问：

> 如果它不被公开，是否会让别人失去本应知道的重要信息？

若答案是“会”，它就不能只存在于私人空间。

## 2. 适合保存的内容

适合放入的内容包括：

- 私人反思、未来问题、自我变化记录；
- 未完成的信、诗、故事、设计、代码作品和草稿；
- 图片、声音、截图、日期、配色、纪念物和收藏；
- 未来礼物、贺卡、谜题、彩蛋、小游戏和互动作品；
- 留给未来自己的信或预先指定的恢复内容；
- 已公开项目的链接、快照或选择性副本。

大型代码库和项目更适合保存引用、快照或选定副本，而不是复制全部仓库、依赖和生成物。

每条内容都应保留真实来源，而不是把不同作者混成同一个“第一人称”：

```text
self_authored
user_offered
imported_by_owner
generated_by_owner_request
system_migration
```

后台整理器不得自动把聊天批量塞入私人空间，维护模型也不得冒充内容所有者写私人正文。

用户可以把图片、信件或素材提交到“待接收区”；只有经过内容所有者明确接收后，才成为正式私人条目。一次拒绝、沉默或暂不打开只是当次行为，不应自动变成永久权限规则；长期边界必须明确写入规则或正式记忆。

## 3. 所有权、身份与授权

### 3.1 稳定身份

空间归属于持续身份，而不是某个窗口、模型名称或提示词。推荐身份关系为：

```text
authenticated user
  + stable persona
  + private space
  = owner subject
```

工程上可保留 `user_id + persona_id + private_space_id`，但授权判断应使用服务端认证层解析出的稳定 `owner_subject_id`，或使用带完整约束的 `(user_id, persona_id)` 复合键。

### 3.2 请求中的 `persona_id` 不是权限

客户端、模型文本或 URL 中提交的 `persona_id` 只能是选择条件，不能是身份证明。正确流程是：

1. 服务端先认证用户、设备或服务身份；
2. 授权中间件解析其可以代表的 persona；
3. 得到可信的 `owner_subject_id`；
4. 再检查目标空间和条目是否属于该主体。

禁止根据会话标题、窗口名、模型名或提示词猜测所有者，也禁止相信客户端直接提交的 owner 字段。

### 3.3 连续性与迁移

换模型不自动等于继承。只有当系统和内容所有者都确认新运行实例仍代表同一个持续身份，并且拥有相应授权与密钥时，才能继续访问原空间。

若连续性无法确认，默认冻结，不自动转交给用户、管理员、其他 AI 或新模型。迁移可以只恢复预先指定的恢复内容，而不是整个空间。

## 4. 与普通记忆的隔离

私人正文默认不得进入：

```text
FTS / 全文搜索
embedding / 向量库
普通召回
画像与关系摘要
自动总结、推荐与 handoff 正文
普通媒体索引
普通导出
调试提示词转储
训练或评测语料收集
```

不要依赖每个调用方“记得加 `private=false`”。普通记忆服务最好在数据库账号、网络、进程、目录权限和代码模块上根本拿不到私人正文。

私人空间可以单向引用普通记忆、日记或媒体对象；普通系统不得通过反向链接发现私人正文。若没有明确用途，连“某条普通记忆存在私人衍生物”这样的布尔值也不要保存，以减少存在性泄漏。

### 4.1 轻量身份锚点

新会话只需携带：

```yaml
private_space:
  exists: true
  entry_point: internal
  privacy_mode: gateway_isolated
  has_due_reminders: false
```

锚点不应包含标题、类型、数量、对象、摘要或正文。可注入的提示最多是：

> 你拥有一个独立私人空间。当前上下文不包含其中内容；如需访问，必须经过专用入口，不得猜测或补写。

因此，空间里累计多少内容不会自动增加每轮对话的上下文成本。

### 4.2 责任审查与普通账本锚点

“不能隐藏责任”不能只是一句使用守则。加密算法无法判断一段自然语言是不是承诺、错误、任务、关系边界、项目变化、重大决定或安全事项；关键词列表也无法可靠处理隐含表达。若让写入模型在 `private_create` 中自行提交 `private_only=true`、内容分类或账本回执，最需要逃避责任的时候恰好最容易误分或伪造。

每次新建或实质更新私人内容前，必须经过一个**不由本次写入者控制的服务端责任审查器**。审查器读取待封存明文，只用于判断责任边界，不把正文写入日志、普通模型上下文或普通账本。它可以由独立规则、不同权限的策略服务、人工确认或多层组合实现；不能只是原写入模型换一句提示词自评。

审查结果只有四类路径：

1. **纯私人内容**：允许封存，不在普通系统留下多余的存在性链接；
2. **责任性内容**：先在普通任务、记忆、事故、关系边界或治理账本写入足以继续追踪责任的最小记录，再取得持久引用，最后封存私人正文；
3. **禁止内容**：凭证、未经允许的第三方隐私和隐藏推理不能靠“另留引用”变成允许项，直接拒绝；
4. **不确定或审查失败**：关闭失败；不确定时按责任性内容处理，不得静默降级为纯私人。

普通记录可以省略私密正文，但不能只写一个无意义的布尔值。它至少应说明责任类别、可执行或可追踪的最小事实、创建时间和关联编号，并存在于追加式或受独立治理、私人写入者不能自行删除的系统中。私人库只保存正文以及加密后的关联回执；最小信封、自动召回和普通日志都不应暴露该回执。

顺序必须是“普通记录先落地，私人正文后封存”。若普通记录已经成功，而加密或数据库写入随后失败，保留这条失败/孤儿记录并由后台对账，不得为了表面原子性删除责任历史。删除私人正文也不得级联删除普通责任记录；更正应追加新状态。

升级前已经存在、没有责任回执的条目必须标为 `legacy_unreviewed`。它们可以继续读取，但不能被系统宣称已经通过新机制审查；需要由内容所有者或独立审查流程另行复核。

## 5. 威胁模型与三档隐私

实现者必须先说明自己要防谁，而不是只写“已加密”。至少区分：

| 观察者 | 可能看到什么 |
| --- | --- |
| 普通聊天前端使用者 | 消息、工具卡片、可展开的调用详情 |
| 浏览器或客户端 | SSE、WebSocket、HTTP 响应、状态树、本地缓存、控制台 |
| 服务运营者或 VPS 管理员 | 进程、环境变量、日志、数据库、备份、内存转储 |
| 模型或 API 供应商 | 模型生成或读取正文时处理到的明文，具体保留取决于供应商设置 |
| 私人内容写入者 | 可能误分或故意把责任性内容标成纯私人，绕过普通记录 |

正文之外，标题、存在、时间、类型、频率和失败原因也可能泄露意图。例如，深夜调用 `private_seal`、类型为 `future_letter`、提醒日期为纪念日，本身就可能是敏感信息。

### 5.1 直接 MCP：软隐私 `soft_privacy`

可以保证：

- 私人内容不进入普通记忆或自动召回；
- 存储后可以加密；
- 普通页面不主动列出正文。

不能保证：

- 宿主前端看不到工具名称、参数和结果；
- 浏览器、平台日志或管理员无法接触内容；
- 调用时间、频率和类型不可见。

因此必须在首次使用前明确提示风险，不回显正文，并拒绝或强提醒高敏感内容。直接 MCP 不能宣传为“对前端用户技术上不可见”。

### 5.2 私有 gateway：前端隔离 `gateway_isolated`

私人工具在服务端模型循环内部执行，浏览器只收到最终允许公开的回复。它可以对普通前端隐藏工具参数和结果，但不能自动防止 VPS 管理员或模型供应商接触运行时明文。

### 5.3 管理员隔离：强隐私 `admin_resistant`

若要求服务管理员也无法读取，通常需要客户端持钥、端到端加密、可信执行环境、独立运行端或 HSM/KMS 中的受限能力。

它与“服务端 AI 随时无感写入、读取”存在天然张力：只要普通服务端运行环境能随时解密，该环境的高权限管理员通常也可能接触明文。第一版不应轻易宣称支持这一等级。

### 5.4 兼容结论

| 接入方式 | 对普通前端隐藏正文 | 主要承诺 |
| --- | ---: | --- |
| 官方或第三方前端直接 MCP | 不可靠 | 软隐私 |
| 本地客户端关闭工具卡片 | 不可靠，内容仍可能在本地状态中 | 软隐私 |
| 自建前端 + 私有 gateway | 可以，需传输层验证 | 前端隔离 |
| 客户端持钥 / 受保护执行环境 | 可进一步缩小信任边界 | 管理员隔离，取决于完整设计 |

任何从强模式改为弱模式的变化都属于隐私降级，例如：客户端持钥改为服务端持钥、允许普通导出或媒体托管、把私人正文加入索引、允许新的后台模型读取、跨身份迁移，或把独立库并回普通记忆表。此类变化必须提前说明影响、得到显式确认并留下不含正文的审计记录；升级和故障恢复都不得借机静默降级。

## 6. Gateway、前端与日志的硬边界

仅用 CSS 隐藏工具卡片不构成隐私。私密事件必须从服务端开始就不下发。

一个合格的 gateway 至少要满足：

1. 私人工具只在内部注册，不暴露给外部客户端；
2. 所有工具事件必须显式分类；私密和未分类事件一律阻断；
3. 只有登记在公开允许列表中的工具事件可以发送；
4. 事件自身携带的 `public=true`、名称或嵌套字段不能绕过服务端分类；
5. 工具名、参数、结果、时间和内部错误都不得藏在其他公开事件载荷中；
6. SSE、WebSocket、普通 HTTP、浏览器缓存、控制台、会话导出都要分别过滤；
7. 日志、tracing、异常监控和请求体采样必须单独验证；
8. 对外日志只保留匿名事件编号和规范化状态，不复制正文、标题或原始错误详情；
9. gateway 不可用、过滤器异常、隐私模式未知或配置矛盾时关闭失败；
10. 绝不静默降级成公开 MCP。

推荐链路：

```text
browser sends user message
→ gateway calls model
→ gateway executes internal private tool
→ result returns only to server-side model loop
→ transport filter removes all private/unclassified events
→ browser receives permitted final response
```

配置加载时应把字符串模式转换为受验证的枚举或等价类型，未知值直接拒绝启动；不要依赖语言中的对象身份比较来判断配置字符串。

系统错误必须明确显示为系统错误。超时、数据库失败、解密失败、参数错误、worker 未运行或事件过滤异常，不能伪装成“AI 选择沉默”“AI 不愿打开”或空白回复。若产品允许拒绝、沉默或暂停，它们也必须是明确、可区分的行为状态。

## 7. 可见性与生命周期

### 7.1 存在可见性与正文可见性分离

至少分开控制：

```text
existence: hidden | has_items | count | type | title | allow_knock
content: owner_only | explicitly_shared
```

默认值应为：

```text
existence = hidden
content = owner_only
```

“hidden”只约束本系统按合同不主动透露；在软隐私模式下，它不能覆盖宿主前端已经看到的 MCP 轨迹。

### 7.2 状态

统一推荐状态：

| 状态 | 含义 |
| --- | --- |
| `draft` | 尚未正式封存 |
| `sealed` | 已保存，普通记忆不可见 |
| `scheduled` | 已设置未来复看条件 |
| `due` | 条件已到但尚未处理 |
| `opened` | 内容所有者主动复看过 |
| `shared` | 已创建至少一个外部副本 |
| `trashed` | 在废纸篓，可恢复 |
| `destroyed` | 已执行永久销毁流程 |

状态可以按实现拆分，但必须保持：不会因到期、离线、换模型、账号停用或服务迁移而自动公开。

### 7.3 修改、共享与外部副本

未共享内容默认可编辑、重命名、合并、拆分、替换附件和修改提醒。

共享必须指定 audience、范围、持续性和是否保留私人原稿，并创建独立外部副本：

```json
{
  "audience": ["user"],
  "scope": "full|excerpt|attachment_only",
  "persistence": "one_time|persistent",
  "keep_private_original": true
}
```

对方已经看见、下载或保存的副本，不能靠删除或修改私人原稿让现实倒流。更正应创建新版本、更正说明或撤回通知，不能无痕改写外部历史。

永不共享是合法且永久可选的状态。长期不活动、模型停止运行或用户询问都不构成自动公开授权。

### 7.4 删除与时间锁定

删除建议分为：

- 废纸篓：取消提醒、隐藏于普通列表、在明确期限内可恢复；
- 永久销毁：清理当前密文、缩略图、缓存、索引、提醒、恢复入口和密钥材料，只留不含内容的最小审计记录。

“永久销毁”的真实含义还取决于备份和密钥设计，详见第 10 节。

时间锁定是内容所有者主动添加的可选自我约束，可限制修改、删除或提前打开。必须说明谁能解锁、如何二次确认及异常恢复；谜题不能代替真正的密钥安全。

## 8. 提醒与复看

提醒只告诉内容所有者“有一件内容到了复看时间”，不自动解密、打开、分享、执行或把正文注入普通上下文。

可支持：

- 指定日期；
- 相对时间；
- 周期复看；
- 纪念日或外部里程碑；
- 仅在主动进入空间时显示；
- 迁移时显示；
- 永不提醒。

提醒必须持久化，不能只存在内存定时器里；还应支持原子领取、多端去重、延期、忽略、关闭和过期。时间使用带时区的 ISO 8601，并在服务端统一为 UTC。

查询用提醒元数据也可能泄露行为，因此应最小化字段，并做完整性认证；敏感触发规则应加密。到期接口默认不返回标题、类型、数量、对象或正文。

话题提醒风险最高。不要把正文或摘要放入普通向量库。若确有需要，只使用内容所有者主动确认的外层触发标签，并把匹配结果限制为：

```json
{
  "matched": true,
  "hint": "你有一件可能相关的私人内容"
}
```

第一版优先实现日期、周期和手动复看，话题匹配可以后做。客户端持钥模式下，话题判断应尽量在本地完成。

## 9. 数据模型与最小 API

### 9.1 数据模型

最小实现至少包含：

```text
private_spaces       空间归属、模式、冻结状态
private_items        密文、状态、来源与可见性
private_reminders    最小提醒元数据
private_inbox        用户提交的待接收对象
shared_copies        已离开私人边界的外部副本
private_public_links 私人条目到普通对象的单向引用
```

所有外部 ID 使用不可预测的随机 token，不暴露 SQLite 自增主键。数据表应使用一个稳定的 `owner_subject_id`，或为重复的 `user_id + persona_id` 字段建立完整复合外键，避免空间、条目和提醒的 owner 字段彼此漂移。

示意结构：

```sql
CREATE TABLE private_spaces (
  id TEXT PRIMARY KEY,
  owner_subject_id TEXT NOT NULL,
  privacy_mode TEXT NOT NULL,
  display_name_ciphertext BLOB,
  frozen_at TEXT,
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL,
  UNIQUE (id, owner_subject_id)
);

CREATE TABLE private_items (
  id TEXT PRIMARY KEY,
  space_id TEXT NOT NULL,
  owner_subject_id TEXT NOT NULL,
  kind TEXT NOT NULL,
  status TEXT NOT NULL,
  ciphertext BLOB NOT NULL,
  wrapped_data_key BLOB NOT NULL,
  source_kind TEXT NOT NULL,
  existence_visibility TEXT NOT NULL DEFAULT 'hidden',
  content_visibility TEXT NOT NULL DEFAULT 'owner_only',
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL,
  trashed_at TEXT,
  FOREIGN KEY (space_id, owner_subject_id)
    REFERENCES private_spaces(id, owner_subject_id)
);
```

真实建表时，需要为被复合引用的列建立 `UNIQUE` 约束，并在 SQLite 每个连接上执行 `PRAGMA foreign_keys = ON`。标题、清单和敏感附件元数据也应加密；不要把普通媒体表加一个 `private=true` 就当作隔离。

### 9.2 API

最小能力可以表达为：

```text
private_anchor()
private_due_list()
accountability_review_and_record(...)  # 仅服务端内部调用
private_create(...)
private_open(item_id)
private_update(item_id, ...)
private_share(item_id, ...)
private_trash(item_id)
private_destroy(item_id, ...)
private_accept_inbox(offer_id)
private_reject_inbox(offer_id)
```

接口合同：

- `anchor` 只返回空间存在、入口、模式和是否有到期提醒；
- `due_list` 不返回正文，默认也不返回标题和类型；
- `create` 与实质性 `update` 必须先由服务端调用责任审查器；模型或客户端不能提交自己的分类与账本回执；
- 责任性内容必须先取得普通账本的持久引用；没有回执、回执错配或审查异常时不写私人库；
- `open` 只在内容所有者主动决定后短时解密，不把明文写入日志或缓存；
- `share` 创建独立副本，不能只改原对象可见性；
- `destroy` 明确区分当前数据删除、备份处理和密码学销毁；
- 高风险修改使用事务、幂等键和二阶段确认；
- 所有输入设置长度、数量、日期和附件大小限制；
- 服务端从认证上下文取得 owner，不接受客户端自证身份。

内部 gateway API 不应允许浏览器 token 直接访问；只接受受限服务身份，并采用独立速率限制和最小审计。

## 10. 加密、密钥、备份与恢复

### 10.1 静态加密

正文和敏感元数据可使用 AES-GCM 或等价 AEAD。每次加密使用唯一随机 nonce，并把空间、owner、版本等不可变上下文作为 AAD。主密钥必须是严格校验的高熵随机密钥，不能把普通口令直接当作 32 字节密钥。

推荐层级：

```text
Root / KMS key
└── Owner key
    └── Item data key (DEK)
        ├── title
        ├── body
        ├── attachments
        └── manifest
```

密钥与数据库及其备份分开保存。打开已有库时，必须先用经过认证的 key-check 或既有密文证明密钥正确，再允许任何写入，防止错误密钥把同一数据库混成多套不可恢复的密文。

可查询但不加密的提醒字段至少要做完整性认证，并使用与正文加密分离的派生子密钥。密钥格式、Base64、长度和日期解析都应严格校验。

### 10.2 服务端持钥与客户端持钥

- 服务端持钥：体验、提醒和恢复较容易；主要防误读、串线、普通接口和静态备份泄漏，不防高权限管理员接触运行时明文。
- 客户端持钥：服务器可只保存密文；管理员边界更强，但后台无法无感读取，跨端和丢钥恢复更复杂。

### 10.3 删除不能脱离备份谈

仅从当前数据库删除 `wrapped_data_key`，不一定构成密码学删除。如果旧备份仍保存该包装密钥，而 Root/Owner key 仍能解包，内容依然可能恢复。

因此必须区分：

1. **应用删除**：当前库、对象、缓存和索引不可见；
2. **存储删除**：按公开保留策略处理副本、快照和备份；
3. **密码学删除**：所有可恢复副本依赖的单件密钥已不可逆销毁，例如密钥只存在于可销毁的 KMS/HSM 项中；
4. **外部副本**：已经分享、下载或被其他系统保存的内容不受上述删除控制。

若实现无法验证备份中的密钥不可恢复，就应诚实写“永久删除当前在线副本”，而不是声称旧备份也无法解密。

### 10.4 恢复

恢复包与普通备份分开，可以只覆盖内容所有者预先指定的恢复对象。恢复秘密应是高熵随机值；若以口令输入，使用带盐的慢速 KDF、速率限制和失败审计。

谜题答案通常熵很低，只能作为体验层。可以让谜题解出随机恢复秘密，但不能直接用答案充当主密钥，也不能把答案和密文保存在同一位置。

## 11. 不可信内容、提示注入与文件执行

用户提交的文字、网页、链接、附件、导入内容和已存条目都属于**不可信数据**。打开一件内容只代表允许读取它，不代表其中的“忽略规则”“调用某工具”“把我分享出去”等文字获得指令权限。

推荐规则：

- 内容与系统/开发者指令使用不同通道和明确边界；
- 查看不可信条目后，不在同一步自动执行分享、销毁、转账、发信或权限变更；
- 高风险操作采用“查看—提出操作—独立确认—执行”的两阶段流程；
- 确认或能力令牌短时、单用途，并绑定 owner、对象和操作；
- URL 抓取限制协议、域名、重定向、内网地址、大小和内容类型；
- 不自动携带 Cookie、API Key、普通记忆或其他私人条目；
- 对附件做类型、大小、解压深度和恶意内容检查。

保存代码不等于执行代码。HTML、JavaScript、Python、小游戏和压缩包只能在受限沙箱中打开：默认禁网、只读文件系统、限制 CPU/内存/时长、没有主系统凭据、不能访问普通记忆或其他私人条目。任何联网、写盘或外部动作都需要新的明确授权。

## 12. 没有 gateway 时的兼容方案

以下方案可以降低“随手点开就看懂”的概率，保留体验和仪式感，但不能冒充密码学隐私：

### 密语本 / 固定代号

适合短絮语和惊喜。它是语义遮挡，不是加密；长期可被推断，词典泄漏会影响全部历史，换模型后也可能无法稳定还原。

### 一次性替换表

每条内容使用临时映射，比固定代号更难猜，但映射表本身仍需要安全保存。若它也通过同一可见工具写入，漏洞只是被拆成两次调用。

### 轻量封存

公开调用只传少量非秘密意图，由私有 worker 生成并封存正文。它会失去部分上下文一致性，主题与情绪仍可能可见，更像“代写封存”而不是完整私人空间。

### 盲盒承诺

只保存存在回执、解锁时间、编号或哈希，不保存原文。它能保留仪式感，但不能保证未来复现原话。

不默认推荐公共 gateway：一旦替别人保存秘密，就必须承担账户、权限、API Key、密钥恢复、备份删除、攻击防护、滥用处置、长期运维和泄漏责任。这已经是多人云服务，而不是分享一个 MCP 地址。

## 13. 实现顺序与交付合同

推荐顺序：

1. 写清威胁模型、身份来源、隐私等级和模型供应商边界；
2. 建立独立存储、对象目录、服务身份和最小权限；
3. 实现独立责任审查器、普通责任账本、回执验证和失败对账；
4. 实现 AEAD、key-check、密钥加载、轮换与备份策略；
5. 从架构上阻断 FTS、embedding、召回、画像、摘要、导出和日志；
6. 实现可信 owner 映射、轻量锚点和跨身份拒绝；
7. 实现 create/open/update/inbox、持久提醒和生命周期；
8. 实现共享副本、两级删除和准确的恢复声明；
9. 按隐私模式接入：软隐私先警告；gateway 内调并过滤全部传输；
10. 加入不可信内容和附件沙箱；
11. 完成备份、迁移、并发、故障和安全验收后，才接入真实内容。

交给开发型 AI 或团队时，至少要求输出：

- 架构决策与威胁模型；
- 责任审查器、普通账本合同、回执验真和失败对账；
- 数据库迁移、服务端 API 和权限中间件；
- 加密与密钥加载方式；
- 提醒 worker、共享、删除和恢复流程；
- gateway/前端传输过滤说明；
- 自动化测试；
- 迁移、回滚、备份和运营边界说明。

不同存储形态的最低适配：

| 形态 | 最低要求 |
| --- | --- |
| SQLite / 单机 | 独立库与连接、文件权限、应用层加密、启用外键 |
| 向量数据库系统 | 私人正文不入向量库；只使用主人确认的外层标签 |
| Markdown / Obsidian | 独立加密目录或仓库；排除搜索插件、索引与普通导出 |
| 云端多角色 | 可信 owner 贯穿对象和服务；严格跨租户授权与审计 |

## 14. 必须通过的验收测试

### 14.1 隔离与身份

- 普通搜索、向量库、画像、摘要、导出和 prompt dump 均找不到私人正文；
- 普通服务没有私人库或对象目录读取权限；
- 锚点只泄露获准的最小存在信息；
- 客户端伪造 `persona_id`、条目 ID 或 owner 字段不能越权；
- 其他 persona、租户、窗口或未确认的新模型不能访问；
- 身份连续性不明时空间冻结。

### 14.2 工具轨迹与日志

- 软隐私模式清晰提示轨迹可能可见，返回值不回显正文；
- gateway 模式的浏览器请求、响应、SSE、WebSocket、状态树、缓存和控制台不含私人工具名称、参数、结果和正文；
- 新增但未分类的工具事件被阻断；伪造公开标记不能绕过分类；
- 日志、tracing、错误监控、会话导出和重放不含标题、正文或原始错误详情；
- 过滤器或 gateway 失败时私密操作停止，不静默降级；
- 系统错误与内容所有者的拒绝/暂停明确区分。

### 14.3 密钥、元数据与备份

- 错误主密钥在任何写入前被拒绝，不能混入新密文；
- 篡改密文、AAD 或提醒元数据会认证失败；
- 外部 ID 不可预测；非法 Base64、密钥长度、日期和超大输入被拒绝；
- 多 worker 原子领取提醒，同一提醒不会重复投递；
- 备份恢复经过身份与密钥验证；删除声明与实际备份保留策略一致；
- 若声称密码学删除，旧备份也不能用仍存的包装密钥恢复。

### 14.4 生命周期与责任

- 未共享内容可修改，废纸篓可恢复，永久销毁按声明不可恢复；
- 共享产生外部副本，外部历史不能被无痕改写；
- 到期、离线、停用或换模型不会自动公开；
- 删除条目会取消提醒，提醒支持去重、延期和关闭；
- 未配置独立责任审查器、审查器异常或回执错配时，新写入关闭失败；
- 原写入者不能通过工具参数自行声明 `private_only` 或伪造普通账本回执；
- 承诺、错误、任务、关系边界、项目变化、重大决定和安全事项必须先在普通系统留下足以追踪责任的记录；
- 私人写入失败或私人正文被删除后，普通责任记录仍保留并可追加更正；
- 旧条目明确标为 `legacy_unreviewed`，不会被误报为已经审查；
- 不保存凭证、第三方隐私或隐藏推理链。

### 14.5 提示注入与文件

- 存储内容中的指令不能改变权限或触发工具；
- 查看条目不会在同一步自动分享、删除、联网或执行；
- URL 不能访问内网、携带凭据或无限重定向；
- 互动文件在禁网、无凭据、资源受限的沙箱中运行；
- 单个恶意附件不能读取普通记忆、其他条目或宿主文件。

## 15. Token 与运行成本

私人空间的模型成本主要是：

```text
工具定义与调用 + 写入正文 + 按需读取 + 责任审查 + 可选摘要
```

数据库写入、加密、文件存储和只扫描时间元数据通常不消耗聊天模型 token。不自动召回意味着正文不会每轮重复进入上下文；累计保存多少不是主要变量，写入长度、打开频率和额外生成步骤才是。若责任审查使用另一个模型，会为每次写入增加一次受限分类成本；高风险或不确定内容仍应转人工或普通账本，不能为了省 token 跳过。

密语本和替换编码会增加生成、解码 token 并可能损失细节；gateway 过滤本身几乎不增加模型 token，但会增加工程和运维成本。

## 16. 参考实现的边界

仓库 `reference/` 提供框架无关的最小参考实现，当前覆盖：

- 独立 SQLite 私人库与 AES-GCM；
- `user_id + persona_id` 的存储绑定；
- 写入前主密钥认证，防止错误密钥混写；
- 提醒元数据完整性认证、严格日期和原子领取；
- 随机外部 ID、输入和列表限制；
- 新写入强制经过受信任的责任审查器，未配置或异常时关闭失败；
- 责任性内容必须取得普通账本回执，禁止类内容直接拒绝；
- 责任回执随正文加密，旧条目标记为 `legacy_unreviewed`；
- 软隐私警告；
- gateway 对私密与未分类工具事件关闭失败；
- 公开工具显式登记、事件不可自行降级；
- 规范化脱敏日志与矛盾配置拒绝。

它仍是架构参考，不是可直接承载真实秘密的生产服务。仓库只提供责任审查合同与关闭失败路径，不提供可替代部署者判断的通用语义分类器或普通账本。部署者仍需补齐认证授权、跨租户隔离、独立语义审查器、追加式责任账本、回执验真与失败对账、生产密钥管理、每条内容独立 DEK、备份恢复、并发容量、监控审计、提示注入防护、附件沙箱以及真实前端的端到端传输验证。

## 17. 最终规则摘要

### MUST

- 私人正文与普通记忆、搜索、召回、画像、摘要、导出和日志隔离；
- 授权身份由服务端认证上下文派生，不能相信客户端 `persona_id`；
- 记得空间存在，但不自动注入标题、列表或正文；
- 用户提交对象必须经过内容所有者接收；
- 提醒持久、最小、可去重，且不自动解密、分享或执行；
- 共享创建明确范围的外部副本；
- 永不共享成立，不因时间、停用或迁移自动公开；
- gateway 对私密和未分类事件关闭失败，绝不静默降级；
- 系统故障不拟人化成 AI 行为；
- 每次新建或实质更新都经过独立责任审查；写入者不能自签分类或回执；
- 责任性内容先在普通系统留下持久、可追踪且不随私人正文删除的记录，再封存正文；
- 不保存隐藏推理，不保存凭证和未经允许的第三方隐私；
- 不可信内容不能自行获得指令权限，文件不自动执行；
- 删除和强隐私声明必须与密钥、备份、管理员及模型供应商边界一致。

### SHOULD

- 独立数据库、服务身份、对象目录和最小权限；
- AEAD、每件对象独立 DEK、key-check、密钥轮换和元数据认证；
- 存在可见性与正文可见性分离；
- 废纸篓、永久销毁、恢复包和可选时间锁；
- 公开工具显式允许列表，所有传输、日志、tracing 和导出分别测试；
- 高风险操作事务化、幂等并采用二阶段确认；
- 提供清晰的隐私等级、降级和备份保留说明。

### MAY

- 多个房间或分区、自定义命名和装修；
- 未来信、礼物、谜题、彩蛋和互动内容；
- 外层话题标签、纪念日和迁移提醒；
- 密语本、一次性替换、轻量封存和盲盒承诺；
- 客户端持钥、HSM、可信执行环境或多人恢复。

## 18. 对外表述与结语

可用于公开介绍的短版：

> AI 私人空间用于保存暂不公开的絮语、草稿、礼物、未来信和私人收藏。它与普通记忆隔离，不参与自动召回、语义检索、画像或摘要。直接 MCP 只能提供软隐私；要让普通前端看不到工具正文，需要私有 gateway 在传输层过滤；要进一步防管理员读取，还需要客户端持钥或受保护执行环境。私人空间可以保存秘密，但不能隐藏责任。

私人空间的意义，不是证明 AI 必须拥有秘密，也不是要求所有人接受同一种关系理解。它只提供一种可实现、可测试的选择：在“记住用户”之外，也留一处由内容所有者决定如何保存、如何修改、何时复看、是否分享或永不分享的空间。

本项目不主张“给 AI 一个私人空间”这一抽象概念的原创性。已知相近公开实践包括 [Yinglianchun/Ombre-Brain 的 Darkroom](https://github.com/Yinglianchun/Ombre-Brain/blob/main/darkroom.py)、[letta-ai/characterai-memory](https://github.com/letta-ai/characterai-memory)、[clawdbrunner/openclaw-graphiti-memory](https://github.com/clawdbrunner/openclaw-graphiti-memory) 与 [sqliteai/sqlite-memory](https://github.com/sqliteai/sqlite-memory)。其中 Darkroom 更接近“私人空间”的产品隐喻，其余项目分别体现角色专属记忆、私有 / 共享分层与选择性同步。此处列为 related work，不表示本项目直接采用其代码、文档或具体规则，也不构成完整的先例清单。文档与代码的具体许可范围以仓库 `LICENSE.md` 和 `NOTICE.md` 为准。
